# Interrupt Injection Across Confidential VM Boundaries — Heckler and WeSee

> **Collection role:** focused laser instance for the Microarch-Isolation TEE/CC chapter; sibling laser to *Speculation Barrier Illusion*.

## Author's Note

There is a sentence that recurs throughout the AMD SEV-SNP and Intel TDX literature, sometimes in marketing material and sometimes in formal specifications: *the hypervisor is removed from the trusted computing base*. The sentence is meant to communicate that memory is encrypted with a key the hypervisor cannot read, that register state at VM exit is encrypted under that same key, and that page-table remapping attacks are detected and refused. All of this is true and all of it is important. None of it covers the interrupt path.

Interrupts are the substrate's escape hatch. They are how the processor stops doing what the running thread asked it to do and starts doing something else instead. In the confidential-computing setting that "something else" is a handler that the guest itself owns and controls — but the *decision to enter the handler*, the *vector that selects which handler*, and the *moment in the instruction stream at which the handler displaces the running code* are all under hypervisor control. The CC guest cannot refuse them. It cannot, in general, even tell whether the interrupt it just received was generated by hardware or synthesised by the hypervisor.

Heckler and WeSee read that asymmetry. They do not argue with it; they exploit it. WeSee chooses the AMD-specific `#VC` exception (vector 29), the one mechanism in the SEV-SNP architecture explicitly designed for guest-to-hypervisor communication, and injects it at moments of the attacker's choosing with an `exit_reason` field the attacker controls. The guest's `#VC` handler — written under the assumption that `exit_reason` is set by the CPU — accepts the crafted value and dutifully copies attacker-selected registers into a shared buffer, where the hypervisor reads them, modifies them, and writes them back. Heckler is broader. It does not target the AMD-specific exception at all; it targets any interrupt handler whose execution has a *global effect* on the running thread — the legacy `int 0x80` Linux syscall handler, signal-delivery paths, any handler that performs a state transition the attacker can usefully time. Heckler works on AMD SEV-SNP and on Intel TDX, because the asymmetry is not an AMD detail — it is a property of the way interrupts are virtualised on commodity x86 silicon.

What both attacks read is that *the architecture asks the guest to trust the hypervisor with interrupt delivery, and provides the guest no primitive with which to verify what was delivered*. That sentence is the laser. Everything else in this writeup is the dissection that establishes it.

The dissection has to be careful because the obvious objection — *just sign the interrupts* — does not survive contact with the silicon. There is no general-purpose primitive on current AMD or Intel parts by which a confidential guest can ask the CPU: "did this exception originate from architectural fault delivery or from an `EVENTINJ` field controlled by the hypervisor?" The information is, in principle, available on the hypervisor side (the hypervisor knows which it did, because the hypervisor either set the field or did not), but it is not exposed to the guest. AMD's documented mitigation, *Restricted Injection*, narrows the set of vectors a hypervisor may inject; it does not produce an authentication primitive. Intel TDX's hardware blocks injection of vectors 0–30 by default; vector 128 (`int 0x80`) is not in that range. The mitigations live one architectural level below the place where the bug structurally lives.

That is the recurring shape of confidential-computing failures in 2024. The protected resource is not the one being attacked. The attack reaches the resource through a *control-flow primitive* that the threat model treated as benign because the substrate the threat model came from (commodity virtualisation) treated it as benign. The fix is the threat model, not the silicon. Heckler and WeSee make that visible at a small enough scale that the structural fact survives the technical detail.

A second observation is worth making in the author's voice because it does not fit cleanly into the technical sections. The Heckler/WeSee result is *small* in the sense that the technical demonstration fits comfortably in a single conference talk and the exploit chains are not, in themselves, more elaborate than typical kernel exploits. The result is *large* in the sense that it relocates a class of attack from "side channels and microarchitectural tricks" to "architecturally specified interfaces working as designed". The relocation is the contribution. A defender who is reading the disclosure record only for novel mechanisms can miss this: the mechanism (event injection) is decades old. What is new is the *context* (the hypervisor is now declared untrusted) and the *consequence* (the decades-old mechanism is now an attack primitive).

This is why the laser case-study format suits the result. A broader survey of CC attacks would describe Heckler/WeSee in a paragraph and move on. A laser instance reads the single anatomy in enough detail that the reader internalises *why* the threat-model relocation matters, and can apply the pattern to the next interface where it recurs. The collection's *Speculation Barrier Illusion* laser does the same work for a different category error (ISA-vs-microarchitecture); both lasers pay the cost of detail in exchange for the structural clarity that detail buys.

The remainder of this writeup is anatomical. §1 lays out what the SEV-SNP and TDX architectures say about who delivers interrupts. §§2–3 dissect Heckler and WeSee respectively at the level of registers and fields. §4 names the common anatomy — the one structural fact both attacks read. §5 describes the mitigation posture. §6 places the work in the literature it speaks to. §7 catalogues the questions that remain open. The piece ends with a relationship statement that locates it within this collection.

## Abstract

The AMD SEV-SNP and Intel TDX architectures protect a confidential guest's memory and register state against a hostile hypervisor through cryptographic confidentiality and integrity. They do not, however, protect the guest against the *interrupt delivery channel*. Heckler [Schlüter et al., USENIX Security 2024] and WeSee [Schlüter et al., S&P 2024] demonstrate that this omission is not a refinement detail but a primitive sufficient to corrupt or extract guest secrets. WeSee uses hypervisor-injected `#VC` exceptions on AMD SEV-SNP, with an attacker-crafted `exit_reason`, to coerce the guest's own `#VC` handler into copying attacker-selected registers into the GHCB shared buffer and writing attacker-chosen values back into the guest's register file. Heckler injects ordinary interrupt vectors — paradigmatically `int 0x80` — to drive guest interrupt handlers whose global effect (modifying registers or signal state) can be steered into an exploitable outcome such as authentication bypass or privilege escalation. The attacks have CVE assignments CVE-2024-25742 (WeSee), CVE-2024-25743 (Heckler signal), and CVE-2024-25744 (Heckler `int 0x80`); AMD and the Linux kernel have shipped partial mitigations. This writeup describes both attacks anatomically, names the structural assumption each invalidates, and positions the result alongside its sibling laser case studies in this collection.

The contribution this writeup makes is neither a new attack nor a new defence. It is a *naming*: the structural fact that both attacks read — *the architecture asks the confidential guest to trust the hypervisor with interrupt delivery, and provides the guest no primitive with which to verify what was delivered* — is stated explicitly, dissected at the level of fields and handlers, and positioned within the broader collection's reading of trust-boundary failures in microarchitectural isolation. The naming matters because it identifies a class of attack (interrupt-injection across CC boundaries) that future disclosures will instantiate from new angles, and because it identifies the corresponding class of fix (an architectural integrity-of-control primitive) that the deployed mitigations are not.

**Keywords:** confidential computing, AMD SEV-SNP, Intel TDX, interrupt injection, `#VC`, GHCB, Heckler, WeSee, trusted computing base, threat model.

## §1. The Interrupt Surface in Confidential Computing

### 1.0 Why interrupts are the interesting surface

Before naming the architectural details, the question of *why interrupts in particular* deserves a paragraph. The CC threat model removes the hypervisor from the trusted computing base by encrypting memory and registers. What it does not remove from the hypervisor is the responsibility for *scheduling*: deciding when the guest runs, when it stops running, and what causes the stop. Scheduling, in the x86 virtualisation model, is enacted through three primitives: explicit VM exits (the guest stops itself by executing an intercepted instruction), preemptive exits (the hypervisor stops the guest by raising a hardware event the guest cannot mask), and event injection (the hypervisor causes the guest to deliver an interrupt or exception to itself).

The first two primitives are observable to the guest in their effect — the guest knows it stopped because it executed `VMMCALL`, or because a timer fired, or because of an external device interrupt. The third primitive — event injection — is observable to the guest only as the *consequence* of the injection: the guest sees that some interrupt arrived, but it cannot directly observe *that the hypervisor injected it*. The observability gap is structural: the field that records the injection (`EVENTINJ.Valid`) lives in the VMCB, and the guest cannot read the VMCB.

This is why interrupts are the interesting surface. Other parts of the hypervisor-guest interface are either authenticated (memory contents through encryption, register state through the VMCB save area's encryption) or directly observable (explicit `VMMCALL` is initiated by the guest itself). Interrupts are the one residual class where the hypervisor exercises control over the guest's behaviour through a mechanism that is neither authenticated nor directly observable to the affected guest. The Heckler/WeSee disclosures are the empirical demonstration that this residual class is exploitable.

### 1.1 What the architecture says

A confidential virtual machine (CVM) on AMD SEV-SNP runs under the same generation of AMD-V hardware as a non-confidential guest, with three additional protections layered on top: memory is encrypted under a per-VM key managed by the AMD Secure Processor [AMD 2020 §2.1]; the VMCB save area is itself encrypted at VM exit, so the hypervisor cannot read or write guest register state directly [AMD 2020 §3.2]; and a Reverse Map Table (RMP) tracks the assigned ownership of every physical page, refusing memory remapping attacks [AMD 2020 §5]. Intel TDX provides the analogous protections through its TDX Module, a measured firmware component that mediates all guest entries and exits, with memory encrypted under a per-trust-domain key managed by Multi-Key Total Memory Encryption (MKTME) [Intel 2023 §2].

The three SEV-SNP protections are each a *different kind* of protection. Memory encryption is a *confidentiality* protection: the hypervisor sees ciphertext, not plaintext. Register-state encryption is a *confidentiality and integrity* protection: the VMCB save area is authenticated as well as encrypted, so a hypervisor that attempts to corrupt the saved state is detected. The RMP is a *structural integrity* protection: the page-table mappings are checked against the firmware-managed map, and rogue remappings are refused. Notably absent from this list is any *integrity-of-control* protection for the interrupt delivery channel. The architectural designers did not omit it from oversight; they omitted it because the threat model that originally motivated SEV-SNP (memory-confidentiality protection against a curious-but-not-malicious cloud provider) did not require it. The subsequent threat-model evolution to "the hypervisor is fully malicious" has not yet been matched by an architectural-protection evolution at the interrupt path.

What neither architecture provides is *authentication of the interrupt delivery channel*. The hypervisor remains the entity that schedules the guest onto a physical CPU, sets up the virtual APIC state, and — by writing the `EVENTINJ` field of the VMCB (AMD) or the equivalent posted-interrupt request descriptors (Intel) — *requests delivery of a specific interrupt vector to the guest on the next VM entry*. The CPU honours that request. The guest's IDT handler for that vector then runs. The guest sees an interrupt; it does not see whether the interrupt was the natural consequence of an architectural fault, a device assertion, or a hypervisor injection.

### 1.2 Who controls what field

Two communication structures matter for the rest of this writeup. The first is the **VMCB (Virtual Machine Control Block)** on AMD; the analogous structure on Intel is the **VMCS**. The VMCB contains:

- the **`EVENTINJ` field** [AMD APM Vol 2 §15.20], which the hypervisor populates to request an interrupt or exception delivery on the next VM entry. The field is hypervisor-controlled. The guest cannot read it.
- the **`EXITINTINFO` field**, which the CPU populates on VM exit to record the cause of the exit. This field is *CPU-set*, but on SEV-SNP it is read by the hypervisor (the hypervisor needs it to virtualise the interrupt correctly) and is *not* directly read by the guest's exception handler — the guest reads its own context, established by the IDT entry.
- the **`exit_reason`** value, which on a `#VC` exception is delivered to the guest through the exception's error code. *This field is set by the CPU on a real `#VC`, but the hypervisor controls what the guest sees if the hypervisor itself injected the `#VC` via `EVENTINJ`.* This is the lever WeSee uses.

The second structure is the **GHCB (Guest-Hypervisor Communication Block)**, an unencrypted shared-memory page that the SEV-SNP architecture specifies as the channel through which guest and hypervisor communicate register state for those operations the guest cannot perform directly (e.g. `RDTSC`, `RDMSR`, MMIO, port I/O) [AMD GHCB Spec 2022 §2]. The GHCB is intentionally *not* encrypted, on the design principle that anything the guest puts in it is something the guest has consciously decided to share with the hypervisor. The architectural soundness of that principle depends on the guest in fact making that decision consciously — i.e., on the guest's `#VC` handler running only when the guest itself wanted a hypervisor service.

A useful way to think about the field-control distribution is as a 2x2 matrix of *who writes* and *who reads* each communication structure. Writes to the encrypted VMCB save area are CPU-only; reads of the encrypted VMCB by the hypervisor are forbidden. Writes to the GHCB are shared (both guest and hypervisor write); reads of the GHCB are likewise shared. Writes to `EVENTINJ` are hypervisor-only; reads of `EVENTINJ` by the guest are not possible. Writes to the guest's IDT are guest-only; reads of the IDT by the hypervisor are technically possible (the IDT lives in guest memory, but its in-memory address is hypervisor-known) but are blocked by SEV-SNP memory encryption — the hypervisor reads ciphertext.

The Heckler/WeSee primitive lives in the asymmetry that *the hypervisor's write to `EVENTINJ` causes a guest-side read of the IDT entry the hypervisor selected*. The hypervisor cannot read the IDT entry, but it can cause the CPU to dispatch to that entry. The asymmetry is not a bug in any single field; it is a consequence of how the fields compose into a control flow that crosses the encryption boundary.

### 1.3 What the guest sees, and what it cannot

When an interrupt fires, the guest CPU walks its IDT, jumps to the registered handler, and executes the handler with the saved state of the interrupted thread. The handler reads:

- the **vector number** (implicitly, from which handler was entered);
- the **error code** (for exceptions that push one);
- the **saved instruction pointer and flags** (from the stack);
- whatever **CPU state** is available through the normal register file.

The handler *cannot* read:

- the source of the interrupt (architectural fault vs. injected);
- whether `EVENTINJ` was set by the hypervisor on the preceding VM entry;
- any cryptographic attestation that the value of the error code originated from CPU logic rather than hypervisor crafting;
- (on AMD) the post-injection value of `EXITINTINFO`, because that field is consumed on the hypervisor side, not exposed in the saved guest state.

In other words: the guest has the interrupt; the guest does not have any primitive by which to verify what kind of interrupt it has. The architectural specification does not provide such a primitive because, in the pre-CVM threat model, the question did not arise — the hypervisor was trusted to deliver interrupts truthfully because the hypervisor was simply trusted.

A subtle and consequential corollary: the guest also cannot verify *that an interrupt did not occur*. If the hypervisor refrains from injecting an interrupt the guest was expecting (e.g., a timer interrupt the guest's scheduler depends on), the guest sees only the absence of the interrupt, and the absence is indistinguishable from a legitimate quiescent period. This *suppression* primitive is not, as far as the published literature reports, exploited by Heckler or WeSee directly, but it is the same shape of architectural gap and merits parallel scrutiny. A guest scheduler that depends on timer interrupts for fairness can have its fairness silently broken by a hypervisor that withholds the timer. A guest watchdog that depends on a periodic interrupt for liveness checks can be silently disabled. The Heckler/WeSee disclosures address the *injection* half of the gap; the *suppression* half remains an open part of the same problem.

### 1.4 The `#VC` mechanism, in detail

`#VC` deserves a dedicated subsection because it is the single field most load-bearing for the WeSee attack and the one most often misunderstood in summaries of the SEV-SNP design.

The `#VC` exception is delivered to the guest on vector 29 when the guest attempts an operation that — under the SEV-SNP intercept policy negotiated at launch — requires hypervisor assistance. The canonical examples are:

- `RDTSC` and `RDTSCP` (the timestamp counter, on platforms where the SEV-SNP firmware intercepts it for normalisation);
- `RDMSR` and `WRMSR` for MSRs the hypervisor needs to virtualise (e.g. the APIC base);
- MMIO accesses to ranges backed by emulated devices;
- `VMMCALL` itself, the explicit hypercall entry point;
- I/O port accesses;
- `CPUID` reads of leaves the firmware intercepts.

On a real, CPU-generated `#VC`, the CPU sets the exception's error code (delivered to the handler through the standard exception-frame mechanism) to identify the operation. The handler reads this value, executes the *Standard Algorithm for Exception Handling* defined in the GHCB specification [AMD GHCB Spec 2022 §2.3.1], populates the GHCB shared page with the required register inputs, performs a `VMGEXIT` to transfer to the hypervisor, and resumes when the hypervisor returns.

The critical structural detail is that `VMGEXIT` is *not* the only way to enter the `#VC` handler. An external `#VC` injection — set by the hypervisor through the `EVENTINJ` field of the VMCB — enters the same handler with the same error-code semantics. The error code value reaches the handler through the encrypted exception frame, but the *value* in that frame is whatever was specified by `EVENTINJ` at injection time. The handler has no architectural way to distinguish the two cases.

This is what WeSee exploits. The other operations Heckler exploits (`int 0x80`, signal vectors) are simpler because they do not even pretend to authenticate; they are ordinary interrupt vectors with ordinary architectural delivery semantics. `#VC` is the case where the architecture has documented a security-relevant communication path *and forgotten to authenticate its source*.

### 1.5 Posted interrupts on Intel TDX

Intel TDX's posted-interrupt mechanism deserves a parallel treatment. Posted interrupts are not specific to TDX — they are an Intel VT-x feature introduced years before TDX — but TDX inherits them and grants the hypervisor write access to the Posted Interrupt Request (PIR) field through the TDX Module.

The PIR is a 256-bit bitmap, one bit per IDT vector, located in a per-VCPU posted-interrupt descriptor in shared memory. The hypervisor sets a bit; the virtual APIC, on the next VM entry, ORs the PIR into the interrupt request register (IRR) and delivers the highest-priority pending vector. The TDX Module enforces that PIR bits 0–30 are masked off (the architectural-exception range), but bits 31–255 are passed through. Vector 128 — `int 0x80` — sits at bit 128 and is therefore reachable. The signal-related vectors Heckler additionally exploits sit even further into the user-defined range and are likewise reachable.

The TDX hardware design recognised the threat of injected architectural exceptions; it did not recognise the threat of injected user-vector interrupts whose Linux-side handlers happen to be load-bearing. The blind spot is the same shape as the SEV-SNP one — a partial, vector-range-based authenticity check standing in for an authenticity primitive.

### 1.6 The assumption invalidated

> *The pre-CVM x86 virtualisation architecture assumed the hypervisor was a benign, trusted intermediary for interrupt delivery. The SEV-SNP and TDX architectures inherit that assumption in the interrupt path, even though they invalidate it in the memory and register paths. The interrupt path is the unrebuilt floor of an otherwise renovated house.*

## §2. The Heckler Attack (Schlüter et al., USENIX Security 2024)

### 2.1 Threat model

Heckler [Schlüter et al. 2024a] assumes a hostile cloud provider running a malicious hypervisor underneath a confidential guest. The attacker has full control over the VMCB / VMCS fields the architecture permits the hypervisor to write — in particular, the `EVENTINJ` field on AMD and the posted-interrupt request mechanism on Intel — and over scheduling, so the attacker can choose when to interrupt the guest at instruction granularity (subject only to the limits of single-step gadget timing on the attacker's hardware). The attacker can read everything the architecture allows the hypervisor to read (memory pages owned by other guests, the GHCB, performance counters), and the attacker cannot read what the architecture forbids (the confidential guest's encrypted pages and its private register state on VM exit).

The attacker's *target* is not the encryption. The attacker's target is *control flow inside the guest's interrupt handlers*. The encrypted state is corrupted, leaked, or bypassed as a consequence of that control-flow effect, not as a direct attack on the cryptography.

### 2.2 Why the attack works at all — the handler's contract

It is worth pausing on a question that the bare description of the attack does not answer: why does the `int 0x80` handler — written by careful kernel developers, audited for decades — accept an arbitrary register state and dispatch a syscall? The answer is that the handler is doing exactly what it was designed to do.

The legacy `int 0x80` ABI is the userspace-initiated syscall ABI from 32-bit Linux. A user-mode program that wants to call a syscall executes `int $0x80` with the syscall number in `eax` and arguments in other registers. The handler is the kernel's syscall entry path. It is supposed to take the userspace registers at face value, look up the corresponding syscall implementation, and dispatch. There is no notion of "this register state might be unintended" in the handler's contract — the contract is that the userspace program owns the register state and the handler executes whatever the userspace program asked for.

The Heckler attack does not lie to the handler. The handler is, from its own perspective, doing the right thing: a `int 0x80` arrived, the handler is executing the syscall identified by `rax`. The lie is to the *userspace program*, which did not execute the `int $0x80` instruction. The lie reaches the handler through a path the handler's contract did not anticipate: an interrupt of vector 128 arriving without a user-mode `int $0x80` having been executed to cause it.

This is the structural shape of the bug. The vulnerability is *between layers*: between the userspace program's intent and the kernel handler's execution. No single layer is buggy. Both layers are doing their jobs. The bug is in the *contract* — the implicit agreement that "vector 128 means the userspace program wanted a syscall" — which the SEV-SNP threat model has invalidated and no architectural primitive has restored.

### 2.3 Mechanism: injecting `int 0x80`

The clearest single instance is the `int 0x80` injection. On x86-64 Linux, the IDT entry for vector 128 (`int 0x80`) is populated to support legacy 32-bit syscall ABIs; it is rarely used by modern user-space code but the handler is *present in the running kernel*. The handler interprets the userspace `rax` as the syscall number, `rbx`/`rcx`/`rdx`/`rsi`/`rdi`/`rbp` as arguments, and dispatches the corresponding kernel routine.

Heckler's mechanism is:

1. The attacker observes guest execution through architecturally permitted side channels — page-fault traces, interrupted-instruction counters — to identify a moment at which the guest is about to enter user-mode code with `rax` already holding a value of operational interest (a return value from a security-critical function, for example).
2. The attacker writes the AMD VMCB `EVENTINJ` field (or sets up the TDX posted interrupt) to request delivery of vector 128 on the next entry.
3. On the next entry, the guest CPU walks its IDT and enters the `int 0x80` handler with the user-mode `rax` taken as the syscall number.
4. The handler dispatches the syscall corresponding to that `rax`. The dispatch has whatever effect that syscall has — and crucially, *the handler typically returns 0 in `rax` on syscall success*, overwriting whatever value was there before.

The chain that converts this into an exploit is straightforward. If the attacker targets a moment immediately after a security-relevant decision is made — `strcmp` returning the comparison result, `setuid` returning success or failure, the credential-validation path of OpenSSH or `sudo` — then the act of injecting `int 0x80` clobbers the decision result with a syscall-handler-defined value, *and the value is typically 0, i.e., "success"*.

The Heckler paper demonstrates concrete chains:

- **OpenSSH authentication bypass.** The attacker times the injection to follow the password-comparison return in `auth_password()`. The handler clobbers `rax`. The caller proceeds as if authentication succeeded.
- **`sudo` privilege escalation.** The attacker times the injection to follow `setuid(0)`. The handler clobbers `rax` to 0. `sudo` interprets this as a successful UID change and executes the requested command as root.
- **Signal-delivery path (CVE-2024-25743).** The attacker injects vectors whose Linux-side delivery interacts with the signal mask of the interrupted thread, modifying signal disposition without the application's consent.

### 2.4 The single-step problem

Heckler relies on injecting the interrupt at a specific instruction. On a non-confidential VM, an attacker hypervisor could simply set the trap flag (`TF`) in the guest `RFLAGS` and inspect every instruction; on SEV-SNP this would require the hypervisor to modify the guest's encrypted register state, which the RMP prevents. The attacker therefore uses *external* signals — page faults induced by remapping non-confidential pages, observable interrupt patterns, performance-monitor unit residue from co-located workloads — to localise the guest's instruction pointer to a window of a few instructions [Schlüter et al. 2024a §5]. The window is wide enough that not every injection lands on the intended instruction, but the attack is statistically reliable across many trials. The attacker only needs the chain to succeed once.

### 2.5 Why TDX is also affected

Intel TDX's hardware blocks the injection of vectors 0 through 30. The intent is to prevent the hypervisor from injecting architectural exceptions whose semantics the guest's handler would mishandle. Vector 128 lies outside that range. The Heckler `int 0x80` mechanism therefore works against TDX with substantially the same anatomy as against SEV-SNP; only the field the hypervisor writes differs (a posted-interrupt request descriptor rather than `EVENTINJ`). The TDX hardware block was designed against a threat model that anticipated injection of architectural exceptions and did not anticipate that *any* injectable vector — including a legacy syscall entry — could be load-bearing.

The TDX-specific anatomy has one additional subtlety. TDX's posted-interrupt mechanism delivers interrupts via the virtual APIC, which on TDX-protected guests is itself a protected resource — the hypervisor cannot read the virtual APIC's local state directly, only write into the PIR. The architectural intent was that PIR writes are *requests* that the virtual APIC processes, not *direct injections* of vectors. In practice, for vectors outside the 0–30 block, the request is honoured nearly unconditionally; the virtual APIC's processing logic does not impose any additional authentication. So while the architectural framing is "the hypervisor requests, the APIC decides", the operational reality is "the hypervisor requests, the APIC delivers" — and the gap is therefore equivalent in effect to the AMD `EVENTINJ` model.

A second TDX subtlety concerns the *handler* side. TDX guests typically run a Linux kernel built with the same `arch/x86/kernel/irq.c` paths as a non-CC Linux kernel, with TDX-specific shims for the operations TDX mediates differently from SEV-SNP. The `int 0x80` handler is one of the unchanged paths. The Heckler-side mitigations described in §5.2 therefore apply equally to TDX guests; the kernel patches are not TDX-specific or SEV-SNP-specific but apply at the externally-injected-interrupt path that both architectures funnel through.

### 2.6 Field-level dissection

```
AMD SEV-SNP injection path:
    Hypervisor → VMCB.EVENTINJ = (Vector=128, Type=External, Valid=1)
    VM entry → CPU honours EVENTINJ → guest IDT[128] entered
    Handler reads guest rax → dispatches syscall
    Handler returns to interrupted RIP with rax := syscall return

Intel TDX injection path:
    Hypervisor → PIR.bit[128] = 1
    TDX_VP_ENTER → virtual APIC delivers vector 128
    Guest IDT[128] entered → same handler semantics as above
```

The structural identity of the two paths is the point. Different chips, different fields, same outcome, because both architectures inherit the same assumption.

Two further fields are worth naming because they appear in the Linux kernel patches that mitigate the attack. `VMCB.EVENTINJ` on AMD has, besides `Vector` and `Type`, an `ErrorCodeValid` bit and an associated 32-bit `ErrorCode` field. For an injected `#VC` (the WeSee target), this field is the surface through which the attacker delivers the crafted `exit_reason`. For an injected `int 0x80` (the Heckler target), `ErrorCodeValid` is normally clear — `int 0x80` does not push an error code in the architectural sense — but a malicious hypervisor can still set it; the guest handler is supposed to ignore the error code for non-error-code vectors, and the patched kernels include a check that verifies this. The check is small but worth noting because it illustrates the operational pattern: every architectural field that the hypervisor can write becomes a candidate for malicious crafting, and every kernel handler that consumes such a field becomes a candidate site for a heuristic-check patch.

### 2.7 The exit-trace asymmetry

A subtlety that bears on later instrumentation work — and one that distinguishes Heckler from WeSee at the observability level — is the VM-exit footprint of the two attacks. WeSee leaves a footprint: an injected `#VC` requires the hypervisor to handle the subsequent `VMGEXIT`, which appears in any hypervisor trace as an ordinary exit with `EXITCODE = VMGEXIT`. The crafted nature of the preceding `#VC` is not visible in the exit record, but the exit record exists. A tracing framework that records every VM exit has a row to inspect.

Heckler's `int 0x80` injection has no such footprint. The hypervisor sets `EVENTINJ` on entry; the guest CPU honours it; the guest IDT handler runs; the handler returns to user mode (or to wherever the interrupt-frame `RIP` pointed). At no point is there a VM exit to the hypervisor — the entire chain executes inside the guest's encrypted context. From the perspective of a hypervisor-level VM-exit log, the attack is invisible. The only artefact is the *absence* of expected events: the program that was supposed to be executing in the guest at that moment is now executing a different code path, but the hypervisor's view does not record that fact.

This asymmetry has practical consequences. A confidential-computing observability framework that relies on VM-exit logs — and many do — has the same capability against WeSee that a non-CC observability framework has against ordinary virtualisation events: the cause is hidden but the existence of *something happening* is recorded. The same framework has zero capability against Heckler: the injection itself produces no log entry, and the consequence (a clobbered `rax`, an unwanted syscall side effect) only manifests downstream in the guest, where the framework does not look. This is a partial-visibility-versus-no-visibility distinction; it is the same distinction that separates speculative-execution attacks (visible only through timing) from architectural attacks (visible through trace).

The implication for instrumented confidential-computing platforms — `seL4`-based confidential hypervisors, for example — is that the *exception bitmap* configured for the guest VMCS becomes load-bearing: a vector that is configured to *not* generate a VM exit when delivered architecturally is also a vector that the hypervisor can inject without generating a VM exit. Closing the Heckler-class observability gap requires either turning every injectable vector into a VM-exit-generating one (expensive, since most injections are legitimate) or instrumenting `EVENTINJ` writes themselves at the platform layer.

### 2.8 The assumption invalidated

> *The guest's interrupt handlers were written under the assumption that an interrupt arriving at vector V was caused by the architecturally legitimate source of vector V — for `int 0x80`, an explicit `int $0x80` instruction executed in guest user mode, or its sysenter equivalent. The SEV-SNP and TDX architectures do not, in their current form, provide a primitive by which the handler can distinguish that case from a hypervisor injection. Heckler reads that gap.*

## §3. The WeSee Attack (Schlüter et al., S&P 2024)

### 3.0 Why WeSee exists separately from Heckler

It is worth stating, before describing the WeSee mechanism, why the Heckler and WeSee disclosures are separate papers and not a single combined publication. The two attacks were developed by the same research group within months of each other; treating them as a single result would have been editorially defensible. The choice to publish them separately reflects, in the author's reading, a methodological judgement: Heckler's `int 0x80` primitive demonstrates the *generic* shape of the interrupt-injection threat, and WeSee's `#VC` primitive demonstrates the *AMD-specific* shape where the architectural specification has, in addition to the generic interrupt-delivery gap, an additional structurally-vulnerable communication channel (the `#VC` handshake itself).

The pedagogical value of the separation is that the two papers cover different aspects of the same anatomy and a reader who internalises both will have understood both the generic interrupt-injection threat (the substrate) and the specific channel-design failure (the AMD addition). A combined paper would have risked conflating the two: AMD readers would have seen the `#VC` finding and treated the generic threat as a side issue; Intel TDX readers would have seen the generic threat and treated the `#VC` finding as not-their-problem. The separation forces both to be read seriously.

### 3.1 The AMD-specific target: `#VC` (vector 29)

WeSee [Schlüter et al. 2024b] is the AMD-specific companion to Heckler. Its target is the SEV-SNP `#VC` (VMM Communication) exception, vector 29. `#VC` exists for a structural reason: an SEV-SNP guest is by design forbidden from performing certain operations directly — reading the timestamp counter, accessing MMIO regions backed by emulated devices, executing some MSR reads — and instead must request the hypervisor's assistance through a controlled handshake. `#VC` is that handshake's entry point [AMD SEV-SNP ABI 2022 §4.1].

The architecturally intended sequence is:

```
Guest executes RDTSC (intercepted)
  → CPU raises #VC with exit_reason = RDTSC
  → Guest #VC handler copies needed registers into the GHCB
  → Guest performs VMGEXIT
  → Hypervisor reads GHCB, writes result, returns
  → Guest #VC handler reads GHCB result back into guest register file
```

The guest's `#VC` handler is the trusted component for this dance. It is part of the guest kernel; it lives inside the confidential boundary. The hypervisor reads only what the handler chooses to copy into the GHCB.

### 3.2 The lever: an injected `#VC`

WeSee inverts the sequence. The hypervisor, instead of waiting for the guest to trigger a `#VC`, *injects* a `#VC` via the same `EVENTINJ` mechanism used in §2. Crucially, the `exit_reason` that the guest handler reads is a value the hypervisor controls — because on an injected `#VC`, the value reaches the handler through the GHCB or through the error-code path, both of which are either shared memory or hypervisor-set fields.

The guest `#VC` handler does not authenticate `exit_reason`. It dispatches on the value. So the hypervisor can make the handler believe the guest just executed `RDMSR`, or `WRMSR`, or an MMIO write, or any other operation in the `#VC` repertoire.

### 3.3 The primitives this yields

The `#VC` handler's dispatch table is, from the attacker's perspective, a menu of register read/write primitives. The handler copies different registers into the GHCB depending on `exit_reason`:

| Crafted `exit_reason` | Registers handler copies | Attacker primitive |
| --- | --- | --- |
| `VMMCALL` | `rax`, `rbx`, `rcx`, `rdx` | Read 4 attacker-chosen guest registers; write 4 attacker-chosen values back |
| `MMIO_READ` | Guest memory range → GHCB | Read arbitrary guest memory the handler will dereference |
| `MMIO_WRITE` | GHCB → guest memory range | Write attacker-chosen bytes into guest memory |
| `RDMSR` | `rcx` (MSR index) | Read attacker-selected MSR value into guest |
| `WRMSR` | `rcx`, `rax`, `rdx` | Write attacker-selected MSR |

Each of these is the *intended* behaviour of the handler for the corresponding genuine operation. WeSee does not require any bug in the handler. It requires only that the handler be entered with a crafted `exit_reason`.

### 3.4 Demonstrated chains

The WeSee paper demonstrates three end-to-end chains [Schlüter et al. 2024b §6]:

- **kTLS session key exfiltration.** In an NGINX server using in-kernel TLS, the symmetric session key passes briefly through `rax` during the kTLS setup path. The attacker localises this moment with page-fault timing, injects a `#VC` with `exit_reason = VMMCALL`, and the handler copies `rax` (i.e., the key) into the GHCB. The hypervisor reads it.
- **Netfilter firewall bypass.** The Linux `nf_hook_slow` routine returns the filtering verdict in `rax`; a value of 0 means *drop*, nonzero means *accept*. The attacker times the injection to land immediately after the verdict is computed, with `exit_reason = MMIO_WRITE` and a GHCB value of 1. The handler dutifully writes 1 into the location backing `rax`. The firewall now accepts the packet it had decided to drop.

  The mechanics of the netfilter chain merit a closer look because they illustrate the *targeting* problem the attacker has to solve. `nf_hook_slow` is invoked once per packet; to bypass a specific firewall rule the attacker needs to inject the `#VC` at the precise moment when `rax` holds the verdict for *the packet the attacker cares about*. The attacker's targeting primitive is, again, page-fault tracing: the attacker arranges (from outside the guest) to send the packet they want to admit, observes the page-fault pattern characteristic of `nf_hook_slow` being entered, and injects in the post-verdict window. Mis-timed injections corrupt the verdict for some other packet; this is harmless to the attacker because they can simply retry until the right packet's verdict gets flipped.
- **Kernel-mode shellcode injection.** The MMIO-write primitive composes into arbitrary kernel writes: the attacker stages shellcode in the GHCB, identifies a virtual address backing a hot kernel function (`nf_hook_slow` again is the example), times the `#VC` injection, and the handler overwrites the kernel text with attacker-controlled bytes. The next invocation of the function executes the shellcode in kernel mode.

The progression of the three chains illustrates the *compositional* nature of the WeSee primitive. The single primitive — coerce the `#VC` handler into reading/writing attacker-chosen state — yields an arbitrary-read in one direction (kTLS key exfiltration), an arbitrary-write in the other direction (firewall bypass), and an arbitrary-code-execution when the write is targeted at executable kernel memory (shellcode injection). The architectural design did not anticipate compositional exploitation because each individual `#VC` operation was treated as a *small step in a benign handshake*, with no attention to what an attacker who can re-enter the handshake with crafted inputs can do across many invocations.

### 3.5 SVSM and #VC handler state observability

A subtlety in the WeSee paper [Schlüter et al. 2024b §3.4] concerns the **Secure VM Service Module (SVSM)**, a privileged component that runs inside the confidential boundary but at a higher privilege than the guest kernel (VMPL0 vs VMPL1+). The SVSM was introduced to handle a class of operations that need to occur inside the CC boundary but at a higher privilege level than the guest kernel itself trusts (e.g. virtual TPM operations). The `#VC` handler's state — the GHCB contents in particular — is observable to the SVSM where the SVSM is present, and this gives the WeSee attacker an additional avenue: if the attacker can drive the `#VC` handler into a state that subsequently passes through SVSM mediation, the SVSM's own behaviour can be steered by the GHCB values the attacker has just controlled. The paper identifies this as a residual vulnerability surface even after the partial mitigations described in §5.

### 3.6 The asymmetry of the field

The WeSee primitive is not "write to the GHCB". The hypervisor can always write to the GHCB — it is shared memory, by design. The primitive is "*cause the guest to read from the GHCB at a moment of the attacker's choosing, with the guest's own handler doing the reading*". That last clause is what gives the attacker the ability to corrupt confidential register state: the handler holds the encryption key (it is part of the encrypted execution context), and the handler's writes into the guest register file therefore land inside the encrypted state. The encryption is, from the attacker's perspective, a transport that delivers attacker-chosen bytes to the precise privileged location they wanted them to land.

### 3.7 A walked example — the kTLS chain at field level

To make §3 concrete, the kTLS chain merits a step-by-step walk at the level of named fields. The setup is an NGINX server inside a SEV-SNP guest, configured to use in-kernel TLS for performance, just having completed a TLS handshake; the symmetric session key is being installed by the kernel's `tls_set_sw_offload()` routine into the per-socket `tls_sw_context_tx` structure.

1. **Attacker localises the moment.** Through page-fault tracing on non-confidential pages — the page tables themselves are owned by the hypervisor for SEV-SNP guests, even though their contents drive access to encrypted pages — the attacker observes the access pattern characteristic of the kTLS setup path. The page faults reveal the function being executed at coarse granularity; performance-counter timing localises further. The attacker now knows, within a window of a few instructions, that the guest is about to execute a `mov` that places the session key into `rax` as part of a copy loop.

2. **Attacker writes `EVENTINJ`.** Just before resuming the guest, the attacker sets `VMCB.EVENTINJ` with `Vector = 29` (`#VC`), `Type = Exception`, `ErrorCodeValid = 1`, `ErrorCode = 0x81` (`VMMCALL`), `Valid = 1`. The `Valid` bit causes the CPU to honour the injection on the next entry.

3. **CPU honours injection.** On VM entry, the CPU's exception delivery logic sees `EVENTINJ.Valid = 1` and treats the request as a pending exception. Before fetching the next instruction in the guest, it walks the guest's IDT[29], pushes the exception frame (including the attacker-controlled error code `0x81`), and jumps to the registered `#VC` handler.

4. **Handler reads `exit_reason`.** The Linux SEV-SNP `#VC` handler (`do_vc()` in `arch/x86/kernel/sev.c`) reads the error code from the exception frame to determine the operation. The value `0x81` is the encoded `exit_reason` for `VMMCALL`. The handler enters the `vc_handle_vmmcall()` branch.

5. **Handler populates GHCB.** The handler copies the guest's current `rax`, `rbx`, `rcx`, `rdx` into the GHCB's save area, sets `GHCB.SwExitCode = 0x81`, and sets the corresponding `ValidBitmap` bits indicating which registers it has populated.

6. **Handler executes `VMGEXIT`.** Control transfers to the hypervisor with a VM exit code of `VMGEXIT`. The encrypted register state is committed to the encrypted VMCB save area; the unencrypted GHCB is now available to the hypervisor.

7. **Hypervisor reads the key.** The hypervisor inspects `GHCB.rax`. The value is the symmetric session key (or its first 64 bits, depending on the kernel's exact handling of the key install). The attacker copies it out to attacker-controlled storage.

8. **Hypervisor returns.** The hypervisor writes back to the GHCB whatever it wishes the handler to read — most simply, the original values, leaving the guest's subsequent execution to appear normal — and resumes the guest. The handler reads the GHCB back into the guest register file (now visible only to the encrypted context), clears the GHCB, and returns from the `#VC` handler. Guest execution continues at the instruction following the one the injection interrupted.

The chain has eight steps, of which exactly one — step 7 — is the attack proper. Steps 1, 2 are attacker preparation. Steps 3–6, 8 are the architecture and the kernel functioning exactly as designed. The "vulnerability" lives between step 4 (handler reads `exit_reason`) and the implicit assumption preceding it: that the value read in step 4 was set by the CPU rather than by the hypervisor in step 2.

This is the structural point the laser register is intended to make visible. Eight steps of legitimate behaviour, hosting one step of attacker reading, with the vulnerability locatable not in any step but in the unstated relationship between two steps. A more conventional advisory would name the bug as "the handler does not validate `exit_reason`"; the anatomical register names it differently — "the architectural specification does not provide a primitive by which the handler *could* validate `exit_reason`". The two namings have different consequences for the fix. The first invites a kernel patch (and indeed, the kernel patch shipped); the second invites a specification revision (and the specification has not been revised).

### 3.8 The assumption invalidated

> *The guest's `#VC` handler was written under the assumption that `exit_reason` was set by the CPU as the result of a guest-initiated intercepted instruction. The SEV-SNP architecture does not authenticate that field across the hypervisor boundary on an injected `#VC`. WeSee reads that gap.*

## §4. The Common Anatomy

### 4.0 What "common anatomy" means in this writeup

The previous two sections described the two attacks separately because they target different vectors and reach different consequences. This section reads them together. The reading is not a synthesis (no new attack is constructed); it is a diagnosis (the structural fact common to both is named explicitly). The diagnostic register is appropriate because, in this collection's framing, the *naming* is the contribution: an attack class that has been named structurally is one that defenders can recognise in new instances; one that has only been described phenomenologically is one that recurs without recognition.

Heckler and WeSee read the same structural fact through two different vectors. The fact is:

> *On AMD SEV-SNP and Intel TDX, the architecture asks the confidential guest to trust the hypervisor with interrupt delivery — both the timing of delivery and the contents of fields the guest's handler consumes — and provides the guest no primitive with which to verify what was delivered.*

The two attacks differ in which property of "interrupt delivery" they exploit:

- **Heckler exploits the timing**: the hypervisor's ability to choose *when* to fire a known-vector handler. The contents (the vector number) are not under attacker control in any non-trivial sense — vector 128 is just vector 128 — but the moment of delivery is. The exploit works because the handler has a global effect on guest state (writes `rax`, modifies signal disposition, etc.), and that global effect, applied at a moment the handler was not designed for, is the primitive.
- **WeSee exploits the contents**: the hypervisor's ability to craft *what* the handler reads when it runs. The timing matters (the attacker still needs to land the injection at a moment when the registers the handler will copy contain something useful), but the load-bearing manoeuvre is the crafted `exit_reason`. The handler runs *correctly* on that crafted value — it is doing exactly what the architecture says to do — and the correctness is the exploit.

### 4.1 The structural-fact statement

The two attacks together establish that the asymmetry is not an incidental property of one handler or one architecture. It is a *property of the threat-model transition* from "trusted hypervisor" to "untrusted hypervisor": certain interfaces that were unproblematic in the first regime become primitives in the second, and the architectural specification has not yet caught up. The fix is the threat model — the spec needs to enumerate which fields cross the boundary, who controls them, and what cryptographic mediation is required — not the silicon, which can be coerced to support the mediation if the architectural designers commit to it.

### 4.2 What is *not* the bug

It is worth naming what the attacks are *not*, because each "not" rules out a class of mitigation.

- **Not a memory-encryption flaw.** AES-XTS on the memory controller continues to function. Confidential pages remain unreadable to the hypervisor through DRAM-direct paths. WeSee's GHCB writes land inside encrypted state through the guest's own handler doing the writing.
- **Not a register-encryption flaw.** The VMCB save area remains encrypted across VM exit. The attacker never reads the guest's saved register state directly; the attacker causes the guest to *copy* its register state into a shared buffer.
- **Not a speculative side channel.** Both attacks are entirely architectural. There is no timing measurement of cache state, no transient-execution gadget, no branch-predictor poisoning. The exploit completes through ordinary, committed instruction execution.
- **Not a software bug in any specific handler.** The Linux `#VC` handler and the `int 0x80` dispatcher are both functioning as their authors intended. The bug is at the architectural specification's silence about authenticity of the calling source.

### 4.3 The structural fact, restated for this collection

The collection's *Speculation Barrier Illusion* writeup names a category error at the ISA/microarchitecture boundary: a property proved about the abstract execution model says nothing about the physical execution mechanism. The Heckler/WeSee writeup names a different category error, at the threat-model boundary: a property assumed about the hypervisor in one threat model continues to be assumed in a later, incompatible threat model. Both errors share a shape — *the assumption that was load-bearing was never stated*, so when the assumption is invalidated the verifier or the architect cannot point at the line that broke.

### 4.4 The dual reading of "trust"

The asymmetry can be stated in another way that clarifies what makes it a *structural* fact rather than a configurable property. The word "trust" in the CC literature carries two distinct meanings that the architectural specification does not currently distinguish.

The first meaning is *confidentiality trust*: a property of the form "X cannot read Y". This is the property SEV-SNP and TDX provide for memory and registers. The hypervisor cannot read the guest's pages; the hypervisor cannot read the guest's registers at VM exit. The property is checked at the cryptographic boundary — encryption with a key the hypervisor does not have.

The second meaning is *integrity-of-control trust*: a property of the form "X cannot cause Y to do Z without Y's consent". This is the property SEV-SNP and TDX *do not* provide for the interrupt delivery channel. The hypervisor can cause the guest's `#VC` handler to run; it can cause the guest's `int 0x80` handler to run; it can cause the guest's signal-delivery path to run. The guest does not consent in any architecturally meaningful sense — there is no signed-request mechanism the guest can use to indicate which interrupts it expects.

The Heckler/WeSee result is that *confidentiality trust without integrity-of-control trust is insufficient*. The cryptographic boundary holds in both attacks; the guest's pages remain encrypted at all times. But the encrypted state is *under the guest's own handlers' control*, and the handlers can be coerced into reading or writing it on the attacker's behalf. Confidentiality protects the storage; integrity-of-control would protect the access pattern; only the former is provided.

### 4.5 The structural fact and the cluster reading

For this collection's cluster reading, the structural fact restates as a pattern: *a security property that is real in one domain (confidentiality of memory) does not transfer to an adjacent domain (integrity of control), and the threat model implicitly conflates them.* This is the same pattern that *Microarch-Isolation* documents at the broader cluster scale — boundaries that the threat model assumes are honoured by the substrate, where the substrate's actual honouring is partial. Heckler/WeSee is the cleanest small example of the pattern because the partial honouring is locatable to a single field (`EVENTINJ`) and a single assumption (its value is benign).

### 4.6 The compositionality observation

A separate observation, less often made in the existing literature, is that interrupt-injection primitives *compose* with other CC-attack primitives in ways that the individual disclosures do not foreground. The WeSee paper demonstrates this at small scale through the chain progression in §3.4 (read primitive → write primitive → code-execution). The general statement is:

- An interrupt-injection primitive that yields *a one-shot register write* composes with a *page-fault-tracing primitive that localises the moment* to yield *write-at-arbitrary-instruction-boundary*.
- A *write-at-arbitrary-instruction-boundary* primitive composes with the *Linux kernel's reliance on specific in-kernel data structures* to yield *targeted kernel-memory corruption*.
- A *targeted kernel-memory-corruption primitive* composes with *the presence of executable kernel pages in known locations* to yield *kernel-mode code execution*.

Each composition step is independently established in the literature; the contribution of Heckler/WeSee is to show that the *first* primitive — the one that the chain begins with — is reachable from the CC threat model. Once that first step is established, the rest of the chain is, from the attacker's perspective, ordinary kernel exploitation.

The compositionality observation has practical consequences for mitigation prioritisation. The Linux kernel patches (§5.2) focus on the first step: they narrow the conditions under which an injection can be performed. They do not address the subsequent steps because those steps are not specific to CC — they are generic kernel-exploitation primitives that have other mitigations (KASLR, kernel hardening, control-flow integrity). The CC-specific layer is the first step alone. This explains why the patches feel narrow: they are addressing the CC-specific contribution and leaving the rest of the chain to general kernel hardening, which is the correct architectural separation but can read as incomplete to a non-specialist.

### 4.7 The assumption invalidated

> *Every interface that the pre-CVM architecture left unauthenticated — because in the pre-CVM threat model authentication of the hypervisor was unnecessary — becomes a candidate primitive in the CVM threat model. The interrupt delivery channel is the most consequential current example. There are almost certainly others.*

## §5. Mitigation Posture

### 5.1 AMD documented response

AMD's documented response to WeSee and Heckler centres on a mode it calls **Restricted Injection** [AMD SEV-SNP ABI 2022 §4.1.9; AMD Security Bulletin 2024-009]. Under Restricted Injection, the SEV-SNP firmware restricts the set of vectors a hypervisor may inject through `EVENTINJ` to a small allowlist (essentially, the vectors corresponding to genuine external device interrupts the guest expects). `#VC`, `int 0x80`, and the signal-related vectors used by Heckler fall outside the allowlist.

Restricted Injection is documented but not enabled by default in any production Linux kernel as of writing. Its activation requires guest cooperation (the guest must request it through a hypercall during boot) and requires the workload to tolerate the restriction — some legitimate vectors are blocked along with the dangerous ones, breaking workloads that depended on hypervisor-injected interrupts. The deployment story is therefore that the architectural lever exists but is under-used.

A second AMD lever, **Alternate Injection**, allows the SVSM (if present) to mediate interrupt injection on behalf of the guest, with the SVSM verifying that the requested vector is one the guest is expecting. This pushes the authenticity check from hardware into a software component, but the component is inside the CC boundary, so the check is cryptographically meaningful. Alternate Injection requires an SVSM and is not yet broadly deployed.

### 5.2 Linux kernel patches

The Linux kernel response was assigned three CVEs and proceeded through two patch streams:

- **CVE-2024-25742 (WeSee).** Patches to `arch/x86/kernel/sev.c` added authenticity checks to the `#VC` handler: the handler now verifies that the operations decoded from `exit_reason` are consistent with the guest's expected state (e.g., that an MMIO operation is targeting a region the guest had previously declared as MMIO, that an MSR operation matches an in-flight `RDMSR`/`WRMSR` instruction). The check is a heuristic, not a cryptographic authentication, because no such cryptographic primitive is available; the check rules out a large class of crafted `exit_reason` values but does not, in principle, close the underlying gap.
- **CVE-2024-25744 (Heckler `int 0x80`).** Patches to the kernel's externally-injected-interrupt handling added a filter: vectors that should never be hypervisor-injected (in particular, vector 128 in a kernel that does not enable the legacy syscall ABI) are detected and refused. The filter is conservative — it refuses some interrupt patterns that, in principle, are benign — and it depends on the kernel's view of what "should never" be injected being accurate.
- **CVE-2024-25743 (Heckler signal-delivery).** The signal-delivery variant remains, as of the latest documented kernel update reviewed for this writeup, only partially mitigated. The signal-mask manipulation primitive is narrower than the `int 0x80` primitive and harder to filter generically; the upstream conversation continues.

### 5.3 Intel TDX response

Intel TDX shipped a TDX Module update widening the hardware-blocked-vector range and adding a configurable per-guest filter that the guest can install at TD creation time to restrict the vectors the hypervisor may post. The update reaches `int 0x80` only if the guest opts in. The pattern is the same as AMD's Restricted Injection: the architectural lever exists, the default leaves it disengaged, and the burden of adopting the mitigation falls on the guest workload's owner.

The TDX response also includes documentation guidance — a recommended set of vectors that guest workloads *should* accept for injection (timer, IPIs, paravirtual device notifications) and a recommended set that they *should not* (legacy syscall, signal-related). The guidance is non-normative; TDX deployers may follow it or not. The non-normative status reflects the same negotiation that §7.6 names: the architecture's specifiers are not yet ready to commit to a normative threat model that lists which vectors must never be injected, because the list would constrain legitimate workloads in ways the specifiers have not finished analysing.

A parallel detail concerns the TDX Module's own measurement. The TDX Module is launched in a measured boot path, and the measurement is part of the attestation that a TDX guest can verify. If a future TDX Module version adds normative interrupt-injection restrictions, the measurement will distinguish module versions that include the restriction from versions that do not. A diligent TDX consumer could, in principle, refuse to run against a TDX Module that does not enforce the restriction. This is the same pattern as AMD's SEV-SNP firmware versioning, where the firmware version is part of the attestation. The attestation primitive *could* carry the threat-model authority that the architectural spec currently does not; whether it will is a deployment-pattern question more than a technical one.

### 5.4 What the mitigation posture actually says

Every mitigation deployed so far is an *allowlist* applied to interrupt delivery — by the hypervisor (Restricted Injection), by the in-CC software (Alternate Injection), or by the guest kernel's external-interrupt filter (the Linux patches). None of them are a cryptographic authentication of the interrupt's source. The architectural primitive that would close the underlying gap — a CPU-set, guest-readable, integrity-protected field that distinguishes injected from architecturally-delivered interrupts — does not exist on current AMD or Intel parts. The literature has begun to discuss what such a primitive would look like [Sridhara et al. 2024]; no production silicon has shipped it.

The practical reading is that Heckler and WeSee are *contained* but not *solved*. The mitigations narrow the attack surface — most interesting injections are now rejected by the guest kernel — but the underlying asymmetry remains, and the next variant attack (one that uses a different vector or a different crafted `exit_reason` value the heuristic allows) is anticipated rather than precluded.

### 5.5 The Linux `#VC` heuristic, in detail

The heuristic that the Linux kernel patch for CVE-2024-25742 installs in `do_vc()` is worth a closer look because it illustrates both the strength and the limit of post-hoc mitigation against an architecturally-unauthenticated channel.

The patched handler proceeds, in outline, as follows:

1. On `#VC` entry, the handler reads the error code as before.
2. The handler also decodes the *interrupted instruction* (the instruction at the saved `RIP` that the `#VC` was reported against). On a CPU-generated `#VC`, this instruction is — by architectural definition — the operation that triggered the exception. On an injected `#VC`, the instruction is whatever the guest was about to execute when the hypervisor injected, which has no reason to match.
3. The handler compares the decoded instruction against the error-code-claimed operation. For `exit_reason = VMMCALL`, the instruction at `RIP` must be a `VMMCALL`. For `exit_reason = RDMSR`, the instruction must be `RDMSR`. For `exit_reason = MMIO_*`, the instruction must be a memory access to an attribute-MMIO range.
4. If the comparison fails, the handler panics the guest kernel: this is a confidential-computing failure-stop posture, on the principle that a non-matching `#VC` is necessarily either an injection or a software bug, and continuing risks corruption.

The heuristic closes most of the WeSee primitive. An attacker who injects `#VC` with `exit_reason = VMMCALL` at a moment when the guest was not about to execute a `VMMCALL` instruction will be caught: the handler will decode the actual instruction, see it is not `VMMCALL`, and panic.

The limit of the heuristic is that the attacker can choose to inject only when the guest *is* about to execute the operation the crafted `exit_reason` claims. This requires the attacker to localise both the timing and the upcoming instruction; both are achievable through the same page-fault and performance-counter side channels the attack already uses. The heuristic raises the cost of the attack — the attacker now has to wait for a window where the upcoming instruction happens to be the operation they want to fake — but does not eliminate it. Particular operations like `VMMCALL` are rare in normal kernel code; particular operations like `RDMSR` are common.

The deeper limitation is that the heuristic does not address Heckler at all. Heckler does not abuse `#VC`; it abuses ordinary interrupt vectors whose handlers have no `exit_reason` to cross-check. The CVE-2024-25744 patch addresses `int 0x80` specifically through a separate check (refusing injected vector 128 in kernels that have legacy syscalls disabled); other vectors remain exposed.

### 5.6 The signal-delivery variant

The Heckler signal-delivery variant (CVE-2024-25743) deserves its own treatment because it is the case where the mitigation gap is most visible. The variant abuses the fact that Linux's signal-delivery path runs as a kernel-mode handler that modifies the signal mask of the interrupted thread. By injecting interrupts at specific moments in the thread's execution, an attacker can cause signals to be delivered (or masked) in patterns that the application did not request.

The exploitable consequences are application-specific. The Heckler paper [Schlüter et al. 2024a §6.3] demonstrates a chain where an SSH session is caused to deliver `SIGUSR1` at a moment when the application's installed handler for that signal performs a privileged action; the result is an authentication-side bypass distinct from but structurally analogous to the `int 0x80` variant.

Mitigation for the signal variant is harder than for the `int 0x80` variant because there is no single vector to filter. Signal delivery is wired through a wide range of architectural events, and the filter would have to enumerate every event that can reach the signal path. The upstream conversation, as of mid-2024 kernel commits reviewed for this writeup, has not converged on a complete filter. Several partial mitigations — restricting signal delivery during specific kernel-mode code paths, adding entropy to the timing — have been merged; the underlying primitive remains accessible in principle.

### 5.7 A taxonomy of mitigation strategies

Reading the deployed and proposed mitigations together yields a four-tier taxonomy of strategies that the community has, in practice, applied to the Heckler/WeSee class:

- **Tier 1 — Allowlist at the architectural layer.** AMD Restricted Injection and Intel's per-guest TDX vector filter. The hypervisor's ability to inject is restricted to a small set of vectors. *Cost:* breaks legitimate workloads that depend on broader injection; requires guest cooperation; not enabled by default.
- **Tier 2 — Allowlist at the privileged-in-CC layer.** AMD Alternate Injection via SVSM. The SVSM (running inside the CC boundary at VMPL0) checks injection requests against a guest-declared expected-vector list. *Cost:* requires SVSM deployment; SVSM is not yet broadly shipped.
- **Tier 3 — Heuristic check at the kernel-handler layer.** Linux CVE-2024-25742 and -25744 patches. The handler decodes the surrounding execution context and refuses interrupts that look injected. *Cost:* heuristic, not cryptographic; defeats most but not all crafted injections; vector-specific.
- **Tier 4 — Application-layer hardening.** Configuration changes that reduce the exploitable surface (e.g. disabling legacy `int 0x80` at kernel build time, hardening signal handlers against unexpected timing). *Cost:* per-workload; does not address the architectural fact; depends on application owners knowing to apply them.

None of these tiers is a primitive that establishes integrity-of-control trust in the architectural sense. They are containment strategies. The architectural primitive (a cryptographically authenticated interrupt-source field, or an opt-in interrupt-shielded mode in which the guest declares which vectors it accepts) has been discussed in vendor documentation but not shipped.

### 5.8 What an architectural fix would look like

The structural conclusion of §5 is that no currently deployed mitigation establishes integrity-of-control trust at the architectural layer. A reader entitled to ask "well, what would?" deserves an answer at least at the level of design sketch.

A design that would close the gap has, at minimum, three components.

**Component 1: a CPU-set, integrity-protected, guest-readable source field.** When an exception or interrupt is delivered to the guest, the CPU writes a field — in encrypted, MAC-protected guest-readable memory — that records the *source* of the event. The field distinguishes (a) architecturally-generated (a real fault or device interrupt), (b) hypervisor-injected via the standard injection mechanism, and (c) (potentially) injected through some authenticated channel the guest opted into. The field is encrypted with the guest's confidential key and authenticated; the hypervisor cannot forge a value.

**Component 2: a guest-side enforcement primitive.** The guest's exception entry path checks the source field against a guest-policy table. The policy table is established at guest boot and is itself part of the attested initial state. Vectors that the guest's policy says "must be architecturally generated" are panic-on-injection. Vectors that the guest's policy says "may be injected" are permitted. The choice of policy is the guest's; the enforcement is the CPU's.

**Component 3: an architectural specification update that names the property.** The CPU and the firmware both have to commit to component 1's semantics, and the commitment has to be normative: a specification statement that says "the source field is integrity-protected against the hypervisor; any silicon implementation that fails to provide this property is non-compliant". Without the normative statement, a future silicon revision could quietly weaken the guarantee.

The three components are not, individually, novel. Component 1 is a standard authenticated-broadcast primitive; component 2 is the same shape as `seL4`'s capability-based gating; component 3 is ordinary specification work. The contribution of articulating them together is to make explicit that *the fix is technically achievable* — the absence of the fix is not a research-state limitation but a deployment-state one.

### 5.9 The assumption invalidated

> *The mitigation posture treats Heckler and WeSee as bugs to be patched in software. The architectural specification continues to treat the hypervisor as the legitimate source of interrupt delivery decisions for a confidential guest. Until the spec changes, every patch is a containment, not a fix. "Not a bug" would be the correct label for the architectural property that the patches are working around; "not a bug" is not what gets shipped.*

## §6. What the Literature Has Shown

The Heckler and WeSee papers do not exist in isolation. They occupy a particular position in a literature that has been building for several years, on the general question of *what residual attack surface remains inside a confidential VM after the cryptographic protections are activated*.

### 6.1 Primary sources

- **Schlüter, B., Sridhara, S., Bertschi, A., & Shinde, S. (2024a). "Heckler: Breaking Confidential VMs with Malicious Interrupts."** *Proceedings of the 33rd USENIX Security Symposium*. The primary technical reference for the Heckler attack chain.
- **Schlüter, B., Sridhara, S., Bertschi, A., & Shinde, S. (2024b). "WeSee: Using Malicious #VC Interrupts to Break AMD SEV-SNP."** *Proceedings of the 45th IEEE Symposium on Security and Privacy*. The companion paper for the `#VC` injection variant.
- **AMD (2022). "SEV Secure Nested Paging Firmware ABI Specification", revision 1.55.** The architectural specification that defines `EVENTINJ`, the GHCB, and the `#VC` handshake.
- **AMD (2022). "Guest Hypervisor Communication Block Standardization", revision 2.02.** The GHCB protocol definition.
- **Intel (2023). "Intel Trust Domain Extensions Module Base Architecture Specification", rev 1.5.** The TDX Module architecture and its posted-interrupt handling.

### 6.2 Antecedents within the CC literature

The literature anticipated the general shape of the problem before Heckler and WeSee named the specific primitive:

- **Van Bulck, J., Piessens, F., & Strackx, R. (2017). "SGX-Step: A Practical Attack Framework for Precise Enclave Execution Control."** *Proceedings of the 2nd Workshop on System Software for Trusted Execution.* The first systematic demonstration that an attacker hypervisor's control over interrupt timing alone — without any cryptographic compromise — is a sufficient primitive against Intel SGX enclaves. Heckler and WeSee can be read as the SEV-SNP/TDX-era successors to this line.
- **Murdock, K., Oswald, D., Garcia, F. D., Van Bulck, J., Gruss, D., & Piessens, F. (2020). "Plundervolt: Software-based Fault Injection Attacks against Intel SGX."** *Proceedings of the 41st IEEE Symposium on Security and Privacy.* Not interrupt-based, but in the same structural family: a primitive the architecture treats as routine (voltage adjustment), used as an attack lever against a trusted enclave.
- **Li, M., Yang, L., Wang, Y., & Lou, W. (2022). "CIPHERH: Automated Detection of Ciphertext Side-channel Vulnerabilities in Cryptographic Implementations."** *Proceedings of the 30th USENIX Security Symposium.* Reads the SEV-SNP ciphertext channel through deterministic encryption; a different primitive from interrupt injection but the same threat model.
- **Li, M., Wilke, L., Wichelmann, J., Eisenbarth, T., Teodorescu, R., & Zhang, Y. (2022). "A Systematic Look at Ciphertext Side Channels on AMD SEV-SNP."** *Proceedings of the 43rd IEEE Symposium on Security and Privacy.* Predecessor work in the SEV-SNP attack surface.

### 6.3 Adjacent and follow-on work

- **Sridhara, S., Bertschi, A., Schlüter, B., & Shinde, S. (2024). "SIGY: Breaking Intel SGX Enclaves with Malicious Exceptions & Signals."** *Cryptology ePrint Archive 2024/710.* A follow-on by the same group that extends the malicious-interrupt primitive into the SGX setting through the signal-delivery path; thematically continuous with Heckler's signal variant.
- **Wilke, L., Wichelmann, J., Sieck, F., & Eisenbarth, T. (2023). "undeSErVed trust: Exploiting Permutation-Agnostic Remote Attestation."** *Proceedings of the 44th IEEE Symposium on Security and Privacy.* Attestation-layer attacks on SEV-SNP, structurally orthogonal to interrupt injection but part of the same residual-attack-surface programme.
- **AMD (2024). "AMD Security Bulletin AMD-SB-3007."** Vendor disclosure of the WeSee vulnerability and the Restricted Injection mitigation.
- **AMD (2024). "AMD Security Bulletin AMD-SB-3008."** Vendor disclosure of the Heckler vulnerabilities.
- **Linux kernel commit history, `arch/x86/kernel/sev.c` and `arch/x86/kernel/irq.c`, May–July 2024.** The kernel patches that implement the heuristic authenticity checks described in §5.

### 6.4 Specification-side and formal-side responses

- **Sridhara, S., Bertschi, A., Schlüter, B., Mehnert, F., & Shinde, S. (2024). "Attestation in TEE-on-Chip Computing: Past, Present, and Future."** A specification-side survey that includes the interrupt-authenticity question as an open architectural item.
- **Coppolino, L., D'Antonio, S., Mazzeo, G., Romano, L., & Sgaglione, L. (2023). "Confidential Computing: Trends, Open Issues, and Future Directions."** Survey paper that anticipates the interrupt-injection class without naming it specifically; useful as evidence that the question was visible to the community before the Heckler/WeSee disclosures.

### 6.5 The seL4 / capability-model position

A separate strand of the literature — the formally verified microkernel and capability-model strand — provides a useful contrast to the Heckler/WeSee result, and the contrast is worth a short section because it sharpens what the AMD/Intel architectural gap actually is.

In the `seL4` capability model, the right to inject an interrupt into a virtual machine is itself a *capability* — a typed reference to an interrupt-handler endpoint that must be presented at the moment of injection [Klein et al. 2014]. Without the capability, the kernel rejects the injection. The hypervisor on `seL4` is therefore unable to inject an interrupt the guest did not previously authorise, because the authorisation is enforced at the kernel layer below the hypervisor. This is not because `seL4` has solved the Heckler/WeSee problem in some general sense; it is because `seL4`'s architectural choice — gate every privileged operation behind an explicit capability — happens to cover the interrupt-injection operation as a side effect.

The contrast clarifies two things. First, the architectural fix to Heckler/WeSee *is technically possible*; `seL4`'s capability gating is an existence proof. Second, the fix is *architecturally invasive*: it requires that interrupt injection become a capability-gated operation, which is a substantial departure from the current AMD/Intel model where injection is a field-write. The current AMD Restricted Injection mitigation is a coarse, vector-range-based approximation of capability gating; Alternate Injection via SVSM is a finer-grained approximation; neither is the full capability primitive.

The further question the `seL4` contrast raises — whether a verified-microkernel-based hypervisor running underneath AMD/Intel CC silicon could itself provide capability-gated injection — has been touched in the literature [Heiser et al. 2020] but not closed. The answer depends on whether the underlying silicon allows the verified microkernel to *enforce* the capability check at the architectural-injection layer (i.e., whether the kernel can be the only entity that writes `EVENTINJ`, with all other code paths gated through it). Current AMD silicon permits this in principle but requires the hypervisor to be the sole writer; on a multi-tenant system, this assumption holds only if the tenant hypervisor is the verified microkernel itself.

### 6.6 What the literature does not yet have

There is, at the time of writing, no formal-methods paper that has modelled the interrupt-injection threat the way the speculative-execution literature has modelled `lfence` semantics. The closest adjacent work is Sridhara et al.'s specification survey, which identifies the gap but does not close it with a verified model. The literature has *identified* the structural fact; it has not yet *formalised* it. This is one of the open questions §7 names.

What such a formalisation would look like is not entirely obscure. A candidate approach would be to extend an existing formal model of x86 virtualisation — Sail-based or Coq-based, depending on the model's lineage — with explicit predicates for interrupt-source authenticity, then check that the guest's exception-handler proofs (which existing models do treat) hold *only when* the predicate is satisfied. A model with the predicate would be able to demonstrate that the Linux `do_vc()` handler, as written before the CVE-2024-25742 patch, has an unsatisfied precondition under an injected `#VC`. The patched handler would have the precondition discharged by the in-handler instruction decode. Formalising this would make the heuristic's coverage explicit and would let the community check that no crafted `exit_reason` can pass the heuristic — a stronger statement than the patch's authors are currently in a position to make.

### 6.7 The assumption invalidated

> *The CC literature had assumed, before 2024, that the residual attack surface against a confidential VM would primarily live in side channels (ciphertext, timing, page-fault). Heckler and WeSee demonstrate that the residual surface includes a purely architectural primitive — interrupt delivery — that had been overlooked because it was, structurally, the same primitive that had been overlooked in pre-CVM hypervisor security. The literature's antecedent assumption — that a CVM threat model would be dominated by side channels — is invalidated.*

## §7. Open Questions

The Heckler/WeSee result leaves a small number of genuinely open questions. The framing here is anatomical: each question is a place where the current literature has identified a gap but no work has yet closed it. Each question is named with the granularity at which a research programme could begin to address it; none is named at the granularity at which a single paper would close it.

### 7.1 Can the architectural primitive that would close the gap be specified without breaking commodity virtualisation?

The most direct fix is a CPU-set, integrity-protected field, readable by the guest's exception handler, that distinguishes architecturally-delivered from hypervisor-injected interrupts. Specifying this is straightforward; making it work without breaking the legitimate cases where a hypervisor *should* be injecting interrupts (timer virtualisation, paravirtualised devices) is harder. The specification has to enumerate the legitimate injection cases, and the enumeration is precisely where the threat-model spec has been silent.

A more minimal version of the same primitive is a per-vector *guest-declared expectation bitmap*: at boot, the guest declares which vectors it is willing to accept by injection and which it is not, and the architectural enforcement is at the bitmap level (any injection of a vector not in the bitmap is dropped by the CPU before reaching the IDT). This minimal version avoids the cryptographic complexity of a signed-field design but trades off flexibility — a guest that later wants to receive a new vector by injection has to update the bitmap, and a malicious hypervisor could refuse to honour an update request. Whether the minimal version is sufficient in practice, and whether it is sufficient *as a temporary measure* while a cryptographic version is designed, are both unresolved.

### 7.2 Does the same anatomy apply to other CC architectures?

ARM CCA, IBM PEF, and RISC-V CoVE all have similar trust-model structures (memory and register state protected, hypervisor untrusted) and similar virtualisation primitives. None of them have, as of writing, a documented analogue of Heckler. Whether this is because the anatomy is different or because the work has not been done is an open question; the parallel to the SGX-to-SEV transition (where SGX-Step's primitive took several years to be recognised as also applicable to SEV) suggests the absence of disclosed attacks is not evidence of architectural immunity.

### 7.3 What is the right primitive for a confidential guest to verify a `#VC`?

The Linux kernel patch is a heuristic: cross-check `exit_reason` against the guest's recent execution history. This rules out blatant crafted values but, in principle, an attacker who could observe the guest's history (through other side channels) could craft a *consistent* `exit_reason`. A cryptographic primitive — for example, a `#VC` payload signed by the secure processor with a key the guest can verify — would be unambiguous but costs hardware. Whether the heuristic suffices in practice, or whether the cryptographic primitive is necessary, is unresolved.

### 7.4 How should formal-methods practice incorporate the interrupt-delivery channel?

`seL4`'s capability model gates interrupt-injection rights at the kernel level; an unprivileged caller cannot inject interrupts at all. This is a constructive answer for `seL4` itself but does not translate directly to a CVM architecture that has to interoperate with commodity hardware. The formal-methods question is whether the verification community can produce a model of CVM interrupt delivery that captures the Heckler/WeSee primitive and can be checked against architectural specs.

### 7.5 What other architecturally-unauthenticated interfaces remain?

Heckler and WeSee identify *one* interface where the pre-CVM threat model's silence carried over into the CVM era. The exception path is the most prominent because it has the broadest semantic impact, but it is not necessarily the only one. The literature has not exhaustively enumerated which architectural interfaces in SEV-SNP and TDX *should* require authentication and *do not*. A systematic anatomical pass would be useful; the present writeup is a single instance of what such a pass might look like.

Candidate interfaces worth that systematic pass include: (a) **MSR virtualisation pass-through** — the set of MSRs the hypervisor is permitted to read or write on the guest's behalf, and whether the guest can verify the values it later reads from those MSRs; (b) **CPUID intercepts** — the values the hypervisor returns for intercepted CPUID leaves, which the guest typically uses to gate feature detection; (c) **the IOMMU page-table walks** for direct-device-assignment paths; and (d) **the timer-source virtualisation** path, where a hypervisor-controlled timer interrupt can subtly skew guest-side timekeeping. Each of these is a place where the architectural specification permits the hypervisor to inject values into a guest-consumed channel, and each is therefore a candidate for the same anatomy that Heckler and WeSee performed against the interrupt channel.

### 7.6 What is the right framing for the "not a bug" statement?

AMD and Intel have, in their advisories, accepted the Heckler and WeSee CVEs and shipped mitigations. The mitigations sit *above* the architectural layer where the property in question would belong. Neither vendor has, in formal architectural specifications, restated the security model to include interrupt authenticity. This leaves the disclosure record in an ambiguous state: the attacks are accepted as bugs at the patch level and as design intent at the architectural level. The collection's *Speculation Barrier Illusion* writeup makes the case that "not a bug" should be a *structural communication* about the model, not a customer-service phrase. The Heckler/WeSee case is the same shape and deserves the same framing.

The asymmetry between *patch-level acceptance* and *architectural-level silence* is the disclosure pattern that the CC literature is, slowly, learning to recognise. A vendor accepts a CVE because the bug is concretely reproducible in shipped software; the vendor does not restate the architecture because doing so would commit to a specific authoritative threat model, and the threat model is still being negotiated between hardware designers, hypervisor authors, and CC consumers. The negotiation is healthy in principle; in practice it produces a disclosure record that lists symptoms (CVEs) without committing to a diagnosis (an architectural property that should hold). The Heckler/WeSee CVEs will read, in five years, as either (a) the early-warning signs of a threat-model rewrite that incorporated interrupt authenticity, or (b) the early-warning signs of a class of follow-on attacks that exploited the same gap from new directions. Which of the two it turns out to be depends on what the next architectural specification revision says.

### 7.7 How should CC-aware observability frameworks handle the asymmetric visibility?

As §2.7 noted, WeSee leaves a VM-exit footprint (the post-injection `VMGEXIT`) but Heckler does not. An observability framework instrumenting a confidential hypervisor — for compliance, intrusion detection, or post-mortem analysis — has partial visibility of WeSee and no visibility of Heckler. The asymmetry is not a software-engineering limitation; it is a consequence of which architectural events generate exits.

The open question is what an observability framework *should* do about this. Three positions are visible in the early literature:

- **Position 1: instrument `EVENTINJ` writes at the hypervisor layer.** Every write to `EVENTINJ` is logged with timestamp, vector, and the guest VCPU's state at the moment of injection. This is technically straightforward but produces high-volume logs and does not, by itself, distinguish legitimate from malicious injections.
- **Position 2: configure the exception bitmap to force VM exits on injected vectors.** This makes every Heckler-class injection visible as a VM exit at the cost of slowing legitimate timer and IPI delivery. Workable for diagnostic builds; not for production.
- **Position 3: instrument the guest kernel.** Add hooks inside the guest's interrupt entry path that log unexpected vectors to a guest-internal log, with the log itself attested. This shifts the trust burden from hypervisor to guest, which is consistent with the CC threat model but requires guest-side cooperation.

None of these positions is settled. The choice between them depends on whether the observability framework's audience is the cloud provider (who wants the hypervisor-side view) or the tenant (who wants the guest-side view). The CC threat model strongly suggests the latter, but the practical operational pressure points the other way.

### 7.8 What is the right framing for *audit* in a CC threat model?

A related question, raised in passing by Sridhara et al. [2024], is whether the concept of *audit* — produce a tamper-evident record of what happened — can survive intact in a CC threat model where the hypervisor is untrusted. Classical audit primitives assume an auditor with privileged read access to the system being audited. A CC threat model denies that access to the hypervisor and grants it only to the guest itself and to attestation-time verifiers. Whether a continuous-audit primitive can be constructed inside this constraint — one that produces records the guest cannot forge and the hypervisor cannot suppress — is an open theoretical question with direct bearing on the Heckler/WeSee detection problem.

### 7.9 What is the cost of moving the threat model?

A pragmatic question often missing from the formal-methods and architectural discussions is what it would cost — in silicon, in software-engineering effort, in workload performance — to ship the architectural primitive that closes the gap. Vendor advisories tend to mention costs only as an obstacle to deployment, not to quantify them. A useful contribution to the discussion would be an honest estimate, by someone with access to the relevant silicon-design data, of the gate count, the cycle-overhead, and the validation burden of (say) a cryptographically-authenticated `EVENTINJ` field. The estimate would let the community judge whether the absence of the primitive reflects a genuine engineering trade-off or a historical inertia that an explicit cost statement would dislodge.

### 7.10 What is the threat-model authority for a CC architecture?

The deepest open question is institutional rather than technical. The Heckler/WeSee gap is, on the technical surface, an authentication question (does the guest know who sent the interrupt?), but the gap *exists in the specification* because no one institutional party currently has the authority to declare what the CC threat model is. AMD's specification says what AMD silicon does; Intel's says what Intel silicon does; the Linux kernel implements what it can on top of both. No party has the standing to say *the CC threat model is that the hypervisor is untrusted, including for interrupt delivery, and silicon must enforce this property*. Establishing that authority — through standards work, through CC consortium engagement, through customer pressure — is the institutional precondition for the technical fix. It is not, in itself, a research question, but the research community can contribute to it by naming the gap clearly and persistently. The present writeup is one such naming.

### 7.11 A closing note on what "open" means here

The questions in §7 are not open in the sense that they have no plausible answer. Each has multiple plausible answers in the existing literature. They are open in the sense that no answer has been *adopted*: no architectural specification has been revised to incorporate one of the proposed primitives, no normative threat-model statement has been published with cross-vendor endorsement, no formal-methods model has been produced that captures the Heckler/WeSee anatomy. Closing the questions does not require novel research; it requires the existing options to be evaluated, chosen between, and committed to. That is an institutional process, and it is the process the disclosure cycle of 2024 has, in the author's reading, made unavoidable. The next architectural specification revision is where the questions are most likely to be closed; until that revision lands, the questions remain open in the precise sense that the laser register requires.

### A.1 The collection's laser/cluster taxonomy

This collection is organised into two formats: **cluster reads** that survey a structural pattern across many instances, and **laser case studies** that anatomise a single instance in enough detail that the structural pattern becomes locally visible. The two formats complement each other. The cluster reads provide the conceptual frame; the laser case studies provide the empirical anchor.

This writeup is one of two **laser case studies** in this collection. It pairs with *Speculation Barrier Illusion* (the speculative-execution laser) as a focused-instance counterpart to the broader cluster reads.

The cluster the laser is embedded in is *Microarch-Isolation*, this collection's broader treatment of trust-boundary failures in microarchitectural isolation. *Microarch-Isolation* makes the general argument that *trust boundaries assumed in the threat model are not always boundaries the substrate honours*. The Heckler/WeSee writeup is one concrete instance of that argument: the trust boundary between a CC guest and the hypervisor was assumed to be honoured by the architecture for all guest-facing resources, but the architecture honours it only for memory and register state, not for interrupt delivery.

The laser also sits in dialogue with three other cluster siblings:

- *Mathematical Collapse* — this collection's read of pre-quantum cryptography's structural exposure to algorithmic advance — establishes the pattern of *a guarantee whose validity was always conditional on an unstated assumption*. The Heckler/WeSee laser instantiates the same pattern at a different scale (architectural, not cryptographic).
- *Silicon Is the Adversary* — this collection's treatment of hardware-level adversarial models — provides the framing within which "the hypervisor is untrusted" becomes a meaningful claim. The laser shows what happens when that claim is half-implemented.
- *SPI-Firmware-Anatomy* — this collection's anatomy of a different unauthenticated interface — establishes the format. SPI flash is to firmware integrity what `EVENTINJ` is to interrupt integrity: an interface that the threat model treats as authenticated and that the architecture leaves unauthenticated.

The pairing with *Speculation Barrier Illusion* is the most direct. Both are laser-scale case studies. Both make a single structural fact visible. Both end with the same statement: the bug is the threat model, not the silicon. Heckler/WeSee is the one of the pair where the threat-model gap is *most cleanly visible*, because the affected resource (interrupt delivery) is named in the architectural spec but its security property is not stated. *Speculation Barrier Illusion* is the one where the affected resource (microarchitectural state) is *not even named* in the relevant spec.

Together, the two lasers cover the two failure modes of an unstated assumption:

- (a) the assumption is stated about an object that exists in the spec (interrupt delivery), but the security property of the object is left implicit;
- (b) the assumption is stated about an object that does not exist in the spec at all (microarchitectural side effects), so no security property can be stated.

Both failures present in the field as "not a bug" disclosures from the vendor. Both are, structurally, the same statement: the threat model has moved, the architectural spec has not, and the gap is exactly where the next attack lives.

## Appendix B — Disclosure Timeline

The Heckler and WeSee disclosures unfolded across several months in late 2023 and 2024. The chronology below is reconstructed from the published papers, AMD and Intel security bulletins, and the Linux kernel commit history; dates are approximate to the month and may differ by a few weeks from primary records.

- **Late 2023.** ETH Zurich research group (Schlüter, Sridhara, Bertschi, Shinde) develops the `int 0x80` injection primitive against SEV-SNP and discovers it generalises to TDX. Independently, the same group develops the `#VC` injection primitive specific to SEV-SNP. The two findings are reported privately to AMD and Intel under coordinated disclosure.
- **Early 2024.** AMD assigns CVE-2024-25742 (WeSee) and CVE-2024-25743 / CVE-2024-25744 (Heckler). Intel acknowledges the TDX-side applicability of Heckler and begins TDX Module development for the wider hardware-block range.
- **March–April 2024.** Papers are accepted at IEEE S&P 2024 (WeSee) and USENIX Security 2024 (Heckler). Preprints appear on arXiv (2404.03526 for WeSee, 2404.03387 for Heckler). AMD publishes Security Bulletin AMD-SB-3007 (WeSee) and AMD-SB-3008 (Heckler).
- **May 2024.** Linux kernel patches for `arch/x86/kernel/sev.c` and `arch/x86/kernel/irq.c` are merged into the mainline. The patches cover the `#VC` heuristic check (CVE-2024-25742) and the `int 0x80` filter (CVE-2024-25744). The signal-delivery variant (CVE-2024-25743) is acknowledged but only partially addressed; upstream discussion continues.
- **August 2024.** Papers are presented at S&P and USENIX Security. AHOI Attacks project pages publish reproduction artefacts.
- **Late 2024.** Intel ships TDX Module updates that widen the hardware-blocked vector range and add the per-guest filter. AMD documents Restricted Injection more prominently in updated SEV-SNP ABI revisions; Alternate Injection via SVSM remains a documented but not broadly deployed mitigation.
- **Through 2025.** Linux kernel iterations refine the heuristic checks; no architectural specification revision incorporating the integrity-of-control primitive of §5.8 is published by either vendor in the period reviewed for this writeup.

The timeline illustrates a recurring pattern in CC-era disclosures: a research-side disclosure, a vendor-side acceptance at the CVE/patch level, and a deferral of architectural-level revision. The present writeup is being authored in mid-2026; if the pattern continues, the next architectural revision to address the gap may not appear until the next major SEV-SNP or TDX generation.

## Appendix D — Glossary of Field Names

For readers who come to this writeup from a software-security background rather than an x86-virtualisation one, the following short glossary lists the architectural fields and structures most heavily referenced.

- **VMCB** — Virtual Machine Control Block. AMD's per-VCPU control structure. Mostly resident in encrypted form on SEV-SNP. Holds guest save area, control area (including `EVENTINJ`), and intercept configuration.
- **VMCS** — Virtual Machine Control Structure. Intel's equivalent of VMCB. Not directly visible to the TDX guest; managed by the TDX Module.
- **EVENTINJ** — Event Injection field in the VMCB control area. Hypervisor-writable. Specifies a vector, type, and (optional) error code to be delivered to the guest on the next VM entry. *The lever both attacks pull.*
- **EXITINFO1 / EXITINFO2** — VMCB exit-information fields, CPU-set on exit. Read by the hypervisor; not directly read by the guest's exception handler.
- **EXITINTINFO** — VMCB field that records the cause of an exit when an interrupt or exception is involved. CPU-set on exit. Distinct from `EVENTINJ` (which is *to inject*); confusingly named.
- **GHCB** — Guest-Hypervisor Communication Block. Unencrypted shared-memory page used by the SEV-SNP `#VC` handshake. *The channel through which WeSee exfiltrates and corrupts state.*
- **#VC** — VMM Communication Exception. AMD-specific exception vector 29. Generated by the CPU on guest-initiated intercepted operations under SEV-SNP. *The vector WeSee injects.*
- **VMGEXIT** — Instruction that performs a VM exit specifically for `#VC` communication, transferring control to the hypervisor after the guest handler has populated the GHCB.
- **PIR** — Posted Interrupt Request. Intel VT-x feature, used by TDX, holding a per-VCPU bitmap of pending interrupts the hypervisor wishes to deliver. *Intel's analogue of `EVENTINJ`.*
- **RMP** — Reverse Map Table. SEV-SNP firmware-managed table that records the ownership of every physical page; refuses memory remapping attacks. Not directly involved in the Heckler/WeSee primitives but mentioned because it is part of the SEV-SNP protection story.
- **SVSM** — Secure VM Service Module. A privileged software component running inside the CC boundary at VMPL0; can mediate hypervisor requests on behalf of the guest. *Potentially a deployment site for Alternate Injection mitigation.*
- **VMPL** — Virtual Machine Privilege Level. SEV-SNP feature providing four privilege levels (VMPL0 highest) within a single CC guest. SVSM runs at VMPL0; the guest kernel typically at VMPL1.
- **MKTME** — Multi-Key Total Memory Encryption. Intel hardware feature underlying TDX memory encryption.
- **TDX Module** — Intel firmware component, measured at TD launch, that mediates all TD-hypervisor interactions. Plays a role analogous to the AMD Secure Processor.
- **IDT** — Interrupt Descriptor Table. Per-CPU table the x86 architecture uses to map interrupt and exception vectors to handlers. Owned by the guest; not directly readable by the hypervisor on a SEV-SNP guest because it lives in encrypted memory.
- **APIC** — Advanced Programmable Interrupt Controller. The x86 mechanism for routing interrupts to specific CPUs and priorities. Virtualised on TDX through the virtual APIC; the PIR mechanism is part of this virtualisation.
- **VMGEXIT** — AMD SEV-SNP instruction that performs a VM exit in the context of a `#VC` handshake, used by the guest after populating the GHCB to request hypervisor assistance.
- **Restricted Injection** — AMD SEV-SNP optional mode in which the SEV-SNP firmware restricts the vectors a hypervisor may inject through `EVENTINJ`. Requires guest cooperation; not enabled by default.
- **Alternate Injection** — AMD SEV-SNP feature that routes injection requests through the SVSM, allowing software-side verification of vector legitimacy. Requires SVSM deployment.

The glossary is non-exhaustive; readers wanting the full canonical names should consult the AMD APM Volume 2 (for SEV/SVM fields) and the Intel TDX Module Base Architecture Specification (for TDX fields). The terms named here are those most heavily relied on by §§1–5 of this writeup.
